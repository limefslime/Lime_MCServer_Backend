# 판매 등록 원본 보관

등록 물품은 플레이어 `NeoForgeData.nfsShopListings`에 `ItemStack.save(registryAccess)`로 저장한다. 이름, 인챈트, 내구도, 모드 Data Components를 포함한 전체 스택을 보관하며 같은 아이템 ID의 서로 다른 스택도 각각 유지한다. 클라이언트가 보낸 이름은 사용하지 않는다.

등록 시 선택 슬롯과 나머지 메인 인벤토리에서 수량을 확인하고 직렬화를 마친 뒤 원본을 차감한다. 오프핸드·장비는 대상으로 삼지 않는다. 취소는 복사한 인벤토리에서 전체 물품의 반환 가능 여부를 먼저 계산한다. 공간 부족이나 읽기 실패이면 원본 보관과 실제 인벤토리를 유지한다. 성공하면 계획한 인벤토리를 적용하고 보관 항목을 제거한다. 물품을 바닥에 떨어뜨리거나 우편에서 새로 생성하지 않는다.

등록·취소의 UI 요청 UUID를 `nfsShopTrades.completed`에 저장한다. 등록은 상품·수량·선택 슬롯·동작이 요청 지문이며, 취소는 상품·동작을 비교한다. 같은 요청 재전송은 최초 결과만 반환하고 `replayed: true`를 표시한다. 같은 ID의 다른 내용이나 상점/우편 동작과의 충돌은 거절한다. 다른 UUID는 새로운 작업이므로 응답 유실 시 임의의 새 요청 ID를 만들지 않는다.

인벤토리·원본 보관·완료 기록·감사 대기 기록은 같은 플레이어 저장 파일에 기록한다. 기존 helper의 중간 저장을 제거하여 완료 기록 없이 물품만 저장되는 구간을 없앴다. 저장 파일을 다시 읽어 Inventory와 저널/등록 보관 데이터를 비교하고 파일 및 디렉터리 fsync를 확인한다. 저장 불확실 상태에서는 인벤토리를 되돌리거나 다시 차감하지 않고 메모리의 완료 기록을 유지하여 저장 확인을 재시도한다.

등록·취소 감사는 월드 `nfs-listing-audit/YYYY-MM-DD.jsonl`에 남긴다. auditId는 플레이어 UUID + 요청 UUID이며 상품, 요청 수량/슬롯, 원래 응답과 시간을 포함한다. 날짜/시간은 UTC다. 파일과 디렉터리를 fsync한 뒤 플레이어의 감사 대기 기록을 지운다. 파일 기록 뒤 player 저장 전에 종료되면 같은 auditId의 줄이 반복될 수 있으므로 이 ID로 구분한다. 부분 쓰기로 남은 마지막 불완전 줄은 재시도 전에 잘라내고 완전한 기록을 보존한다. 파일을 자동 삭제하지 않는다.

저장/감사 실패 시 UI는 완료를 기다리는 표시를 유지하고 100 tick 복구에서 확인한 뒤 최종 응답을 받는다. 상점·우편과 같은 저장 확인 및 리스폰 데이터 복사를 사용한다. 감사 대기 복구가 실패하면 새 등록/취소 및 새 결제/수령 작업을 시작하지 않는다. 접속하지 않은 플레이어의 감사 대기는 다음 접속 후 복구한다.

등록은 아직 다른 플레이어가 구매하는 거래소가 아니다. 서버 상점 거래는 보관 수량을 건드리지 않는다. 상점/우편 지급 복구는 S2_game_trade_recovery.md와 S2_mail_recovery.md를 참고한다. 기존 requestId 없는 등록의 자동 이전은 하지 않는다.

## 검증 상태

Java 21/Gson으로 실제 `ListingRequestReceipts`를 실행하여 등록·취소 재전송, 상품/수량/슬롯/동작 충돌, 저장 실패 뒤 완료 기록을 이용한 재시도, 최초 결과 보존을 확인했다. 이 테스트의 인벤토리는 단순 상태 모델이며 실제 ItemStack/NBT를 검증하지 않는다. `ListingAuditWriter`는 실제 임시 파일에서 fsync·반복 auditId·줄바꿈이 포함된 이름·쓰기 경로 실패·불완전 tail 복구를 검증했다.

기존 프로토콜·인벤토리 알고리즘과 모드팩 검증도 통과했다. 전체 NeoForge 빌드와 게임 NBT 저장 시험은 Gradle 의존성 확보 문제로 남아 있다. 아래 절차를 실제 게임에서 수행해야 한다.

## 게임 검증 절차

1. 별도 테스트 월드와 백업을 준비한다. 이름·인챈트·내구도·모드 Components가 다른 동일 아이템들을 등록하고 재로그인 및 정상 서버 재시작 뒤 수량과 원본 속성을 확인한다.
2. 취소 후 각 스택의 Components와 전체 수량을 등록 전과 비교한다. 서로 다른 Components가 섞이거나 기본 아이템으로 바뀌지 않아야 한다.
3. 인벤토리를 채워 취소한다. 오류가 표시되고 인벤토리와 등록 목록에 변화가 없어야 한다. 일부 공간만 비워도 전체 반환이 불가능하면 그대로 유지되어야 한다.
4. 충분한 공간을 확보한 뒤 취소한다. 원본을 한 번만 반환하고 다시 취소하면 listing not found로 거절해야 한다.
5. 보관한 아이템의 서버 상점 구매·판매를 수행한다. 보관 수량과 Components는 변하지 않아야 한다.
6. 수량 부족·유효하지 않은 슬롯·중복 등록을 확인한다. 수량 부족은 차감 없이 거절하고, 슬롯 범위 밖이면 메인 인벤토리에서 확인하며, 추가 등록은 원본 스택을 추가 보관한다.
7. 읽을 수 없는 스택/누락된 모드의 저장 데이터를 사용한 복구 시험에서는 취소가 거절되고 데이터가 남아 있어야 한다. 정상 모드 환경과 백업으로 복구한다.

기존 메모리 전용 등록은 영속 파일이 없었으므로 자동 이전할 수 없다. 기존 서버가 살아 있다면 업그레이드 전에 해당 등록을 취소하고 물품을 확인한다.

8. 동일 등록 UUID를 재전송하고 인벤토리 차감·보관 수량·감사 ID가 추가되지 않는지 확인한다. 같은 UUID의 상품·수량·슬롯·동작 변경은 거절해야 한다.
9. 취소 완료 후 같은 UUID를 재전송한다. 원본을 다시 지급하지 않고 최초 결과를 반환해야 한다. 그 사이 같은 상품을 새로 등록했어도 새 보관을 취소하면 안 된다.
10. 등록/취소 저장 직전·직후에 강제 종료하고 Inventory, nfsShopListings, completed와 listingAudit를 대조한다. 물품 상태와 완료 기록이 같은 저장 버전이어야 한다.
11. player 파일 권한/디스크/fsync 및 감사 경로 쓰기를 각각 실패시킨다. UI는 대기하고 물품을 반복 변경하지 않아야 한다. 저장 공간을 복구한 뒤 완료 응답과 감사 파일을 확인한다.
12. 감사 줄 기록 뒤 player의 감사 완료 저장 전에 종료한다. 복구 후 같은 auditId 반복을 허용하되 서로 다른 ID로 새 작업을 만들지 않아야 한다. 부분 JSON 줄 뒤 재시도는 완전한 줄들을 유지하고 읽을 수 있는 새 줄을 남겨야 한다.
