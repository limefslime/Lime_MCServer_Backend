# 판매 등록 원본 보관

등록 물품은 플레이어 `NeoForgeData.nfsShopListings`에 `ItemStack.save(registryAccess)`로 저장한다. 이름, 인챈트, 내구도, 모드 Data Components를 포함한 전체 스택을 보관하며 같은 아이템 ID의 서로 다른 스택도 각각 유지한다. 클라이언트가 보낸 이름은 사용하지 않는다.

등록 시 선택 슬롯과 나머지 메인 인벤토리에서 수량을 확인하고 직렬화를 마친 뒤 원본을 차감한다. 오프핸드·장비는 대상으로 삼지 않는다. 취소는 복사한 인벤토리에서 전체 물품의 반환 가능 여부를 먼저 계산한다. 공간 부족이나 읽기 실패이면 원본 보관과 실제 인벤토리를 유지한다. 성공하면 계획한 인벤토리를 적용하고 보관 항목을 제거한다. 물품을 바닥에 떨어뜨리거나 우편에서 새로 생성하지 않는다.

인벤토리와 보관 데이터는 같은 플레이어 저장 파일에 기록된다. 변경 직후 vanilla 플레이어 저장을 요청한다. 디스크 저장 실패를 별도로 확인하는 영수증이나 WAL은 없으므로 저장 실패까지 복구가 보장된다고 볼 수 없다. 서버를 멈추고 `.dat` 백업을 보존한 다음 원인을 해결해야 한다.

등록은 아직 다른 플레이어가 구매하는 거래소가 아니다. 서버 상점 구매·판매는 기존 백엔드 흐름을 사용하며 등록 보관 수량을 건드리지 않는다. 결제 후 응답 유실, 재전송 멱등 처리, 우편 지급 복구는 후속 단계다. 등록 요청의 동일 requestId 재전송도 아직 멱등 처리하지 않으므로 실패 응답만으로 반복 제출하지 말고 목록/인벤토리를 먼저 확인한다.

## 검증 상태

기존 백엔드 테스트 8개와 모드팩 오버레이 테스트 2개는 통과했다. 이 테스트는 이번 Java 보관 흐름을 검증하지 않는다. Java 빌드는 Gradle의 foojay-resolver 의존성 다운로드에서 중단되어 컴파일과 실제 게임 검증이 남아 있다.

## 게임 검증 절차

1. 별도 테스트 월드와 백업을 준비한다. 이름·인챈트·내구도·모드 Components가 다른 동일 아이템들을 등록하고 재로그인 및 정상 서버 재시작 뒤 수량과 원본 속성을 확인한다.
2. 취소 후 각 스택의 Components와 전체 수량을 등록 전과 비교한다. 서로 다른 Components가 섞이거나 기본 아이템으로 바뀌지 않아야 한다.
3. 인벤토리를 채워 취소한다. 오류가 표시되고 인벤토리와 등록 목록에 변화가 없어야 한다. 일부 공간만 비워도 전체 반환이 불가능하면 그대로 유지되어야 한다.
4. 충분한 공간을 확보한 뒤 취소한다. 원본을 한 번만 반환하고 다시 취소하면 listing not found로 거절해야 한다.
5. 보관한 아이템의 서버 상점 구매·판매를 수행한다. 보관 수량과 Components는 변하지 않아야 한다.
6. 수량 부족·유효하지 않은 슬롯·중복 등록을 확인한다. 수량 부족은 차감 없이 거절하고, 슬롯 범위 밖이면 메인 인벤토리에서 확인하며, 추가 등록은 원본 스택을 추가 보관한다.
7. 읽을 수 없는 스택/누락된 모드의 저장 데이터를 사용한 복구 시험에서는 취소가 거절되고 데이터가 남아 있어야 한다. 정상 모드 환경과 백업으로 복구한다.

기존 메모리 전용 등록은 영속 파일이 없었으므로 자동 이전할 수 없다. 기존 서버가 살아 있다면 업그레이드 전에 해당 등록을 취소하고 물품을 확인한다.
