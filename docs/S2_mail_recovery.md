# 우편 수령과 아이템 지급 복구

우편 수령은 DB 영수증과 게임의 기존 `ShopTradeJournal`을 연결한다. 별도 지급 저장소를 만들지 않고, 상점/우편 중 플레이어당 하나의 대기 작업을 유지한다.

## 백엔드

`POST /mail/:mailId/claim`에 `playerId`, `requestId`(둘 다 UUID)를 전달한다. 지갑 → 우편 순서로 row lock을 잡고 소유자를 확인한 뒤 수령 처리한다. `(playerId, requestId)` 영수증을 조회하여 같은 요청은 최초 결과를 반환한다. 동일 요청 ID를 다른 우편에 재사용하면 409, 다른 요청 ID로 이미 수령한 우편을 받으려 해도 409다. 다른 소유자의 우편은 404로 거절한다.

수령 표시·금전 보상·원장·영수증·감사 outbox를 같은 트랜잭션에 기록한다. 중간 실패나 잔액 overflow는 전부 롤백하며 다음 재시도를 허용한다. 잘못된 item_reward 태그나 범위를 벗어난 수량은 우편을 소비하지 않고 409로 거절한다. 확정된 서비스 오류는 playerId/requestId/mailId/code를 포함하여 게임에서 요청을 대조할 수 있다. 5xx·프록시 오류·ID 충돌은 지급을 확정하지 않는다.

기존 본문 없는 수령 API는 응답 형식을 유지하지만 재전송 보호/새 소유자 확인 대상이 아니다. 새 Java 경로는 항상 두 ID를 보낸다. 구버전에서 이미 수령한 우편은 새 영수증이 없어 자동 재지급하지 않는다.

## 게임

우편 수령 전 `nfsShopTrades.pending`에 서버 생성 요청 UUID와 우편 ID를 저장하고 Inventory/저널 저장 확인 및 fsync 후 HTTP를 보낸다. 금전은 백엔드가 한 번 지급한다. 검증한 itemReward는 인벤토리 전체 삽입이 가능할 때만 지급한다. 공간이 부족하거나 아이템을 읽을 수 없는 경우 결과를 보관하고 재시도한다. 기본 아이템의 ID/수량만 지원하며 우편 보상에 별도 Data Components는 추가하지 않았다.

아이템 지급과 완료 기록·pending 삭제는 같은 player `.dat`에 기록한다. 재시작·로그아웃·리스폰 후에는 같은 backend 요청을 재확인하거나 저장된 결과에서 지급을 이어간다. 저장이 불확실하면 상태를 되돌리지 않고 저장 확인을 재시도한다. 완료된 UI 요청 재전송은 물품을 새로 만들지 않고 결과만 반환한다. 우편 UI는 대기 표시를 유지하되 공간 확보를 위해 닫을 수 있다.

## 배포와 검증 상태

기존 DB에 019 → 020 → 021을 적용한 다음 백엔드와 모드를 함께 업데이트한다. UI 프로토콜은 10으로 변경하여 클라이언트도 함께 업데이트해야 한다. Ubuntu 파일/디렉터리 fsync와 vanilla/NeoForge 플레이어 저장 구조를 전제로 한다. 월드와 DB의 서로 다른 시점 수동 복구는 영수증·인벤토리를 함께 대조해야 한다.

자동 검증은 Node/PGlite 실제 서비스 테스트와 Java 21/Gson 응답 검증을 포함한다. 금전+아이템, 아이템만, 알림 우편, 동시 재시도, 다른 ID 재수령, 소유자 불일치, requestId 재사용, 영수증/outbox 실패 롤백, overflow, 잘못된 item 태그, legacy 호환을 확인한다. Java 검증은 우편/요청/소유자·보상 일치, 수량·타입 검증, proxy/5xx/충돌 거부를 실행한다.

전체 NeoForge 빌드는 기존 Gradle foojay-resolver 의존성 다운로드 실패로 미완료다. PGlite 테스트는 실제 PostgreSQL 다중 연결의 lock 경합을 증명하지 않는다. NBT 직렬화·강제 종료·아이템 실제 지급 시험은 아래 체크리스트로 별도 수행해야 한다.

## 실제 게임·운영 시험 대기

1. 금전만/아이템만/혼합/알림 우편 수령 후 mail flag, wallet, ledger, receipt, audit와 Inventory를 비교한다. 같은 요청 재전송에 추가 지급이 없어야 한다.
2. DB commit 직후 HTTP 응답을 차단하고 서버 재시작·재로그인한다. 동일 요청 영수증을 통해 원래 보상을 한 번 지급해야 한다.
3. accepted 저장 직후·아이템 지급 완료 저장 직전/직후에 강제 종료한다. player `.dat` Inventory와 pending/completed, DB 영수증을 대조한다.
4. 인벤토리를 채워 아이템 우편을 받는다. pending 결과가 남고 우편 UI를 닫을 수 있어야 한다. 공간을 확보하면 전체 지급하고 바닥에 드롭하지 않아야 한다.
5. 지급할 아이템의 모드를 제거한 상태에서는 보관해야 한다. 올바른 모드를 복구한 뒤 완료되어야 한다.
6. 저장 권한/디스크/fsync 장애 시 수령 전에는 HTTP를 보내지 않고, 완료 상태에서는 아이템 재생성 없이 저장만 재확인해야 한다.
7. 다른 플레이어의 우편, 다른 mailId의 영수증, 일반 proxy 404, 5xx, request conflict 응답은 소비·지급으로 처리하지 않아야 한다. 확정된 already claimed 응답은 자동 재지급하지 않아야 한다.
8. 상점 작업 중 우편 수령, 우편 지급 대기 중 상점/판매 등록 변경을 요청한다. 하나의 대기 작업만 유지해야 한다. HTTP 도중 로그아웃·사망·리스폰도 시험한다.
9. 실제 PostgreSQL 두 연결의 동일 수령/서로 다른 수령 및 상점·퀘스트 동시 작업을 시험한다. 감사 파일 쓰기 장애 중 outbox를 보존하고 복구 후 JSONL로 기록되어야 한다.

판매 등록 요청 멱등 처리도 연결했다(S2_listing_escrow.md). 별도 후속: API 전체 인증, 완료 기록 보관/관리 정책. legacy 수령 이후 지급 누락은 자동 판단하지 말고 감사 기록과 player 데이터를 확인해 복구한다.
