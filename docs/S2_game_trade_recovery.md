# 게임 결제 대기열과 물품 복구

상점 구매·판매의 Java 경로는 `ShopTradeJournal`로 통합했다. 메인 서버 스레드에서 플레이어별 하나의 거래를 준비하고 HTTP는 최대 2개 worker에서 처리한다. 대기 요청은 100 tick마다 다시 확인하며, 접속을 끊은 플레이어는 다음 접속 후 복구한다. 사망으로 플레이어 객체가 교체될 때 거래 저널과 판매 등록 보관도 새 객체로 복사한다.

## 저장과 상태

`NeoForgeData.nfsShopTrades.pending`에 UI 요청 UUID, 별도 서버 생성 backend UUID, 상품/수량/방향, 단계, 판매 원본 스택을 저장한다. `completed`에는 UI 요청별 결과와 완료 기록을 유지한다. 다른 거래로 같은 UI 요청 ID를 재사용하면 거절한다. 서버 생성 UUID는 백엔드 `shop_trade_receipts`와 연결된다.

- `queued`: 판매 원본을 메인 인벤토리에서 보관한 뒤, 인벤토리와 대기열을 같은 player `.dat`에 저장한다. 파일을 다시 읽어 Inventory와 저널이 일치하는지 확인하고 파일/부모 디렉터리를 fsync한 경우에만 HTTP를 전송한다.
- `accepted` / `rejected`: 요청과 정확히 일치하는 백엔드 응답을 저장한다. 확정된 구매면 물품을 지급하고 확정된 판매면 보관을 끝낸다. 확정된 판매 거절이면 원본 스택을 돌려준다. 반환 공간 계산은 복사본으로 수행하여 일부 지급이나 바닥 드롭을 하지 않는다.
- 완료: 인벤토리 변경, 완료 기록, 대기열 삭제를 같은 플레이어 저장에 기록하고 확인한 뒤 UI에 최종 결과를 전송한다. 같은 UI 요청이 다시 들어오면 완료 결과만 반환한다.

네트워크 오류·5xx·응답 파싱 실패·요청 내용 불일치·requestId 충돌은 대기 상태를 유지한다. 임의의 4xx 응답만으로 원본을 반환하지 않는다. 요청 식별자, 상품, 수량, 방향과 알려진 오류 코드/status가 일치하는 서비스 거절만 확정 처리한다. Java와 백엔드를 함께 업데이트해야 이 오류 응답 형식을 사용할 수 있다.

저장 확인 실패 후 인벤토리를 되돌리지 않는다. 이미 디스크에 새 상태가 저장되었을 가능성이 있기 때문이다. 해당 플레이어의 메모리 상태를 유지하고 이후 tick에서 저장 확인을 재시도하며 그동안 추가 결제/판매 등록 변경을 막는다. 완료 기록은 재전송 안전성을 위해 자동 삭제하지 않는다.

## 운영 조건과 한계

기존 DB에 019 → 020을 먼저 적용하고, 이번 백엔드와 게임 모드를 함께 배포한다. UI 네트워크 프로토콜을 9로 올려 구버전 클라이언트의 대기 응답 오해를 막으므로 모든 클라이언트도 같은 모드로 업데이트한다. 기존 모드의 저널 없는 거래는 자동 이전하거나 복구할 수 없다. 구매는 상점의 기본 아이템을 지급하며 판매 실패 반환은 원본 Components를 보존한다. 거래 대상으로 메인 인벤토리를 사용하고 오프핸드·장비는 사용하지 않는다.

저장 검증은 vanilla/NeoForge의 플레이어 저장 파일 위치와 NBT 구조를 전제로 한다. 운영 대상인 Ubuntu 로컬 파일 시스템에서 파일 및 디렉터리 fsync가 지원되어야 한다. 지원하지 않거나 저장 구조를 바꾸는 모드가 있으면 결제를 보내지 않고 대기한다. 월드와 DB를 서로 다른 시점으로 수동 롤백하면 중복·유실 위험이 생기므로 백업 복구는 함께 검토해야 한다. 완료 기록 증가와 오프라인 플레이어의 대기 거래는 운영 점검 대상이다.

우편 수령 지급 복구는 같은 대기열로 연결했다(S2_mail_recovery.md). 판매 등록 requestId 멱등 처리와 API 전체 인증은 별도 작업이다. 플레이어 활동 통계는 부가 처리이며 저장 장애 직후 완료된 거래의 통계는 누락될 수 있다. 거래 원장/감사 로그가 결제 기준이다.

## 자동 검증

Node/PGlite 서비스 테스트와 HTTP 거절 응답 형식을 검증한다. Java 21 + Gson으로 실제 `ShopTradeProtocol`을 컴파일하여 영수증/거절 식별 일치, 타입·금액·수량 검증, 충돌/5xx/프록시 응답 거부를 실행한다. `TradeInventoryPlan`은 fixture ItemStack으로 병합, 다른 Components, 부족한 공간에서 무변경, 여러 원본의 전체 반환, 스택 한도 분할을 실행한다. 이 fixture는 실제 Minecraft ItemStack/NBT를 구현하지 않으며 NeoForge 기동·직렬화·저장 장애 검증을 대체하지 않는다.

실행: `JAVA_HOME=<JDK21> SHOP_TEST_GSON_JAR=<gson.jar> python -m unittest discover -s tests -p 'test_shop_java.py'`. Java 전체 모드 빌드는 Gradle foojay-resolver 의존성 다운로드 실패로 아직 미완료다.

## 실제 게임 검증 대기

1. 정상 구매·판매 뒤 잔액, stock, ledger, 영수증, Inventory, pending 삭제와 completed 기록을 비교한다. 동일 UI UUID 재전송이 물품을 다시 지급/회수하지 않아야 한다.
2. backend를 중단한 채 판매한다. 원본 Components가 pending에 남고 추가 거래/등록 변경이 거절되어야 한다. 게임 재시작·재로그인 뒤 backend를 복구하면 동일 backend UUID로 한 번 정산해야 한다.
3. backend가 결제를 commit한 직후 응답을 차단한다. DB 영수증 replay로 복구하며 구매 지급/판매 차감이 한 번이어야 한다.
4. queued 저장 직전/직후, 응답 단계 저장 직후, 인벤토리 완료 저장 직전/직후에 각각 별도 백업 월드로 강제 종료 시험한다. 파일과 DB 영수증을 대조하여 원본 또는 지급 물품이 한 곳에 있어야 한다.
5. 구매 확정 뒤 인벤토리를 채운다. 지급이 pending에 남고 공간 확보 뒤 전체 지급되어야 한다. 판매를 서버 정책으로 거절한 뒤 원본을 반환할 공간이 부족해도 같은 규칙을 지켜야 한다.
6. 이름·인챈트·내구도·모드 Components가 서로 다른 동일 아이템을 판매 거절시켜 원본을 비교한다. 복구 도중 필요한 모드를 제거하면 읽기 실패로 보관해야 한다.
7. 저장 권한 제거·디스크 부족·directory fsync 실패를 각각 시험한다. queued 저장을 확인하지 못하면 HTTP를 보내지 않아야 한다. 완료 저장 불확실 상태에서는 물품을 다시 지급하지 않고 저장만 재시도해야 한다.
8. HTTP 500·HTML 404·다른 UUID의 200·requestId conflict를 전달한다. 물품을 반환하거나 완료 처리하지 않아야 한다. 실제 409 재고 부족/잔액 부족·429 쿨다운은 일치하는 오류 응답인 경우에만 안전하게 끝내야 한다.
9. HTTP 진행 중 로그아웃/재접속, 서버 stop/start, 사망·리스폰, UI 닫기·다시 열기를 확인한다. 오래된 player 인스턴스에 물품을 지급하지 않아야 한다.
