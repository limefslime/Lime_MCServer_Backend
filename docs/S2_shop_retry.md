# 상점 결제 재시도

`POST /shop/buy`, `POST /shop/sell`에 기존 `playerId`, `itemId`, `quantity`와 선택 필드 `requestId`(UUID)를 전달할 수 있다. 한 거래를 재시도할 때는 같은 ID와 같은 거래 내용을 사용한다. 새 ID는 새 결제다. ID를 생략한 기존 게임 서버 요청은 기존 응답 형식을 유지하지만 중복 결제 방지 대상이 아니다.

영수증은 플레이어 UUID + 요청 UUID를 키로 저장한다. 해당 플레이어의 지갑을 먼저 잠근 뒤 영수증을 확인한다. 완료된 요청이면 현재 가격·재고·활성 여부·거래 쿨다운을 재검사하지 않고 최초 결과와 `replayed: true`를 반환한다. 같은 ID로 상품·수량·매수/매도 방향을 바꾸면 HTTP 409를 반환한다. 잘못된 요청 UUID는 400이다. 최초 응답에는 `requestId`, `transactionType`, `replayed: false`가 추가된다.

지갑·재고·원장·거래 기록·영수증·감사 outbox는 같은 DB 트랜잭션이다. 중간 실패는 전부 롤백하며 영수증을 소비하지 않는다. requestId 없는 거래도 감사 outbox를 남긴다. 기존 감사 writer가 `logs/audit/integration-YYYY-MM-DD.jsonl`에 fsync 후 기록 완료를 처리한다. `AUDIT_LOG_DIR`로 경로를 지정할 수 있다. 파일과 DB 사이의 장애로 감사 줄이 반복될 수 있어 auditId 기준으로 구분한다.

## 적용

기존 DB에 마이그레이션 019 다음 020을 적용하고 백엔드를 업데이트한다. 신규 파일을 저장소에 추가하는 것만으로 기존 PostgreSQL 컨테이너에 자동 적용되지는 않는다. 영수증을 임의 삭제하면 오래된 요청이 새 결제가 될 수 있으므로 삭제 정책은 아직 두지 않는다.

## 범위와 다음 단계

현재 Java 서버는 requestId를 전달하지 않으며 자동 결제 재전송도 추가하지 않았다. 백엔드의 중복 결제 방지만으로 게임 인벤토리 중복 지급·유실을 막을 수 없다. 다음 단계는 게임 서버가 결제 전 원본 판매 물품/구매 요청을 영속 보관하고, 동일 요청을 재전송하며, 완료 기록과 지급·회수를 함께 저장하는 것이다. 우편 수령도 별도 복구가 필요하다. 기존 상점 API 인증 변경은 이번 작업 범위에 포함하지 않았다.

## 검증

PGlite PostgreSQL 엔진에서 실제 서비스와 관련 마이그레이션을 사용해 구매·판매 재시도, 가격/활성/재고 변경 후 영수증 반환, 요청 내용 충돌, 구매·판매 중간 실패 롤백, 잔액 부족 후 재시도, UUID 검증/대소문자/플레이어별 범위, 기존 요청 호환, 감사 JSONL 기록을 확인한다. PGlite는 단일 엔진에서 트랜잭션을 직렬화하므로 여러 실제 DB 연결의 row-lock 경합 증명은 아니다.

운영 전 별도 PostgreSQL에서 두 연결로 같은 최초 요청을 동시에 보내고, 응답 유실 뒤 재전송하며 잔액·재고·원장·영수증·감사가 각각 한 번만 변경되는지 확인한다. 서로 다른 requestId의 거래가 두 번 적용되는지, 상반된 거래가 기존 쿨다운을 지키는지도 확인한다. 감사 파일 쓰기 실패 중 거래가 outbox에 유지되고 저장 복구 후 기록되는지 점검한다.
